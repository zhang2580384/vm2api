# v2.4.3 · 升级后出口设置不丢失

修复独立维护流程中的配置加载缺陷：升级后的槽位服务刷新可能绕过数据库初始化，将已保存的域名转发及自定义 DNS 配置替换为默认值。面板里的设置仍然显示正确，实际运行出口却已改变，进而导致槽内浏览器加载失败、登录超时或质量探针持续“无法判断”。

## 修复了什么

- **维护与面板使用同一配置源**：独立维护先加载对应项目数据库，再刷新槽位服务和出口，沿用代理池已保存的域名转发、DNS 首选及 DNS 类型设置。
- **覆盖相关维护入口**：包括升级后的服务刷新、滚动维护、旧集群槽位迁移与对齐脚本。
- **异常时停止维护**：数据库不存在、项目与已打开数据库不匹配或备份恢复尚未完成时，禁止继续执行维护，避免用默认值覆盖原运行设置；自行打开的数据库连接在维护完成或失败后关闭。
- **验证实际运行配置**：回归测试会替换真实 Linux 出口进程，并核对新进程使用的 JSON，确认域名转发和自定义 DNS 都已保留。

## 哪些部署建议升级

使用域名转发、自定义 DNS，并通过升级流程刷新槽位服务的部署建议更新。部分代理按 IP 连接失败、按域名连接正常，配置回落会使问题更明显。此类网络错误发生在取得有效响应之前，不能据此认定账号或模型降级。

质量运维规则保持：明确检测不通过时，按任务配置关闭调度；**“无法判断”仅记录，不关闭调度**。本版不自动切换代理、开启调度或重新登录账号。

## 升级与恢复

1. 使用面板正常更新，或将镜像固定为 `ghcr.io/zhang2580384/vm2api:v2.4.3`。升级会重启控制面，请先结束当前浏览器操作，并保留原有持久化挂载、环境变量和 Compose 配置。
2. 正常更新流程会使用新版本的独立服务刷新脚本，重新生成保存设置对应的运行出口。**相关出口会短暂断开并重新连接。**
3. 若手动拉取镜像并重建控制面，请在服务健康后执行配套维护命令（容器名按实际部署替换）：

   ```sh
   docker exec vm2api node /opt/vm2api/scripts/fleet-services.mjs
   ```

4. 再手动执行一次质量检测；需要浏览器时结束旧任务后重新打开。本版修复出口配置加载，不保证第三方验证或账号授权结果。

已保存的代理池设置仍在时，无需重新导入代理。不要通过反复更换账号或重建槽位代替恢复运行出口。
